# simple-hpke 0.3.0 -- implementation spec

Status: agreed, not yet implemented.
Supersedes: `docs/notes.md` (that directory is gitignored and gets wiped
by `npm run build-docs`, which runs `typedoc ./src/index.ts` and cleans
its output dir).

This is a deliberate breaking release. The consuming chat app updates in
lockstep, so no deprecated aliases are carried forward.

## Definition of done

1. The API below ships as 0.3.0.
2. `commitmentForKey` is deletable from the consuming app.
3. Every error thrown by this library is an `HpkeError` with a `code`.
4. Tests cover the new surface (list in "Tests" below).
5. README and CHANGELOG updated, with `BREAKING CHANGE:` entries.

## Explicit non-goals

- **The wire format does not change.** No version byte, no envelope
  bump. Envelopes produced by 0.2.x still open under 0.3.0 and vice
  versa. The known-answer fixture test in `test/index.ts` must keep
  passing untouched.
- **Wrong key, wrong `info`, and tampered bytes stay indistinguishable.**
  They all surface as `ERR_DECRYPT_FAILED`. Splitting them would give an
  attacker a decryption oracle. This is a feature, not an omission.
- **`open.raw` keeps returning bare `Uint8Array`.** No `keyId`, no
  object wrapper. Callers who want the id can hash the bytes themselves
  or import and call `keyId`.
- **`encrypt` / `decrypt` return shapes are untouched.** The hybrid path
  never hands a long-lived key back to the caller, so there is nothing
  to fingerprint.

## Target API

```ts
create(recipient, opts?:{
    size?:128|256
    info?:Uint8Array|string
    extractable?:boolean
}):Promise<{ wrapped:Uint8Array; key:CryptoKey; keyId:string }>

encryptKey(recipient, aesKey?, opts?:{
    size?:128|256
    info?:Uint8Array|string
    extractable?:boolean
}):Promise<{ wrapped:Uint8Array; key:CryptoKey; keyId:string }>

open(keypair, wrapped, opts?:{
    info?:Uint8Array|string
    extractable?:boolean
}):Promise<CryptoKey>

open.raw(keypair, wrapped, opts?):Promise<Uint8Array>   // unchanged

keyId(key:CryptoKey):Promise<string>
verifyKeyId(key:CryptoKey, expected:string):Promise<boolean>

class HpkeError extends Error { readonly code:HpkeErrorCode }
```

## Change 1: `enc` -> `wrapped`

The returned field is renamed. No alias, no deprecation window.

Rationale: in RFC 9180, `enc` names the encapsulated key alone (the KEM
output), not the sealed payload alongside it. A reader who knows HPKE
assumes there is a second ciphertext field to persist and goes looking
for it. The value we return is `enc ‖ ciphertext`.

`wrapped` is chosen over `envelope` for two reasons. First, `open`'s
parameter is already named `wrapped`, so producer and consumer now
agree. Second, the README already uses "envelope" for the *other* wire
format (`wrappedLen ‖ wrapped ‖ iv ‖ ciphertext`, produced by
`encrypt`); reusing the word for both would reintroduce exactly the
ambiguity being removed.

Edits:

- `src/index.ts` `encryptKey`: return `{ wrapped, key, keyId }` instead
  of `{ enc: wrapped, key }`. The local variable is already named
  `wrapped`.
- `src/index.ts` `create`: destructure and forward the new shape.
- `src/util.ts` `encryptBytes`: change
  `const { enc, key } = await encryptKey(...)` to destructure `wrapped`,
  and update the two uses in the `concat(...)` call.
- JSDoc across both files: every "The `enc` bytes returned by `create`
  or `encryptKey`" becomes "The `wrapped` bytes returned by ...".
- README: all `enc` destructuring in examples.

Note the internal `encap()` return value keeps its `enc` field. That one
genuinely is the RFC's `enc`, and it is not public API.

## Change 2: `extractable` option, default `false`

Today `create`, `encryptKey`, and `open` all hand back an extractable
AES key, because `importAesKey` hardcodes `true`. The consuming app then
has to keep the room conversation key -- the key that decrypts every
stored message -- extractable in memory for the entire session, purely
so it can hash it. That sits badly next to
`assertPrivateKeysAreNonExtractable` in the same app, which throws if an
identity private key is extractable.

New default: the returned key is **non-extractable** unless
`opts.extractable === true`.

Precise semantics:

- `opts.extractable` governs only keys **this library imports or
  generates**.
- If `aesKey` is a `CryptoKey`, `encryptKey` returns **that same object,
  unchanged** -- same extractability, same usages, same identity. See
  Change 2b.
- If `aesKey` is a `Uint8Array`, it is imported with the requested
  extractability.
- If no `aesKey` is given, the generated key is imported with the
  requested extractability.
- `open` imports the recovered key with the requested extractability.
- `decryptBytes` is unaffected. It already uses
  `importAesKeyDecryptOnly` (non-extractable, decrypt-only) because that
  key never leaves the library.

Edits:

- `src/index.ts`: `importAesKey (raw, extractable = false)` -- thread the
  flag through instead of hardcoding `true`.
- `src/index.ts`: add `extractable?:boolean` to the `opts` type of
  `create`, `encryptKey`, and `open` / `openBytes`.
- While here, fix a latent type bug: `openBytes` and `openRawBytes`
  currently declare `opts?:{ info:Uint8Array|string }` with `info`
  **required inside the object**, so `open(kp, w, {})` is a type error
  for no reason. Make it `info?:Uint8Array|string`.

Callers who need raw bytes have two paths that do not require an
extractable key: `open.raw(...)`, or `opts.extractable: true` where they
really want an exportable `CryptoKey`.

### Change 2b: a supplied `CryptoKey` comes back untouched

`encryptKey` currently re-imports a caller-supplied `CryptoKey` and
returns a *different* key object. With `extractable` defaulting to
`false`, that would silently hand back a downgraded copy of the key you
passed in.

New behavior: if `aesKey` is a `CryptoKey`, the returned `key` is that
same object. `opts.extractable` is ignored for that case.

Known consequence, accept it: a supplied key that lacks the `'encrypt'`
usage previously still worked through `encrypt()` (because the
re-import granted `['encrypt', 'decrypt']`). It will now fail inside
`subtle.encrypt` with a WebCrypto error. This is the correct outcome --
the library should not silently launder a key's declared usages -- but
document it in the `encrypt` JSDoc.

The export-and-validate path is unchanged: a supplied `CryptoKey` must
still be extractable (its raw bytes are what get sealed) and must still
be 16 or 32 bytes.

## Change 3: `keyId` and `verifyKeyId`

### Naming

Called `keyId`, not `commitment`. In this literature "commitment"
already means key-committing AEAD -- binding a ciphertext to exactly one
key, e.g. to defeat partitioning-oracle attacks. What we are building is
a key fingerprint. Calling it `commitment` would mislead a
crypto-literate reader in precisely the way `enc` misleads an
HPKE-literate one (Change 1).

### Derivation

```
keyId = base64url( SHA-256( utf8("simple-hpke key-id v1") ‖ rawKeyBytes ) )
```

43 characters, unpadded base64url, via `uint8arrays`' `toString`.

The label is domain separation: it guarantees this value cannot collide
with a bare `SHA-256(rawKey)` computed elsewhere for some other purpose.

This is **not** byte-compatible with the app's existing
`commitmentForKey`, which is plain `base64url(SHA-256(raw))`. Any
commitments already persisted must be migrated or recomputed. Confirmed
as acceptable.

Publishing this digest is safe: the input is 128 or 256 bits of
uniformly random key material, so preimage recovery is infeasible. Say
so in the README, because the property depends on the key being random
and a reader may not notice that.

Add to `src/constants.ts`:

```ts
export const KEY_ID_LABEL =
    new TextEncoder().encode('simple-hpke key-id v1')
```

### The registry

WebCrypto has no digest-a-key primitive, and `exportKey` is the exact
operation Change 2 exists to forbid. So the id cannot be recomputed from
a non-extractable `CryptoKey`. The library instead records it at the
moment it still holds the raw bytes:

```ts
const keyIds = new WeakMap<CryptoKey, string>()
```

`WeakMap` so a registered key does not leak; entries die with the key.

Registration points, all in `src/index.ts`:

- `encryptKey`, on the key it returns -- generated, imported from bytes,
  or supplied by the caller. All three cases get registered, since in
  all three the function holds `keyBytes`.
- `openBytes`, on the key it returns.
- **Not** `decryptBytes`. That key never escapes the library.

`encryptKey` computes the id eagerly so it can populate the `keyId`
return field. That is one extra SHA-256 per call over ~32 bytes:
negligible.

### `keyId(key)`

```ts
export async function keyId (key:CryptoKey):Promise<string>
```

1. WeakMap hit -> return it.
2. Miss, and `key.algorithm.name !== 'AES-GCM'` -> throw
   `HpkeError('ERR_UNKNOWN_KEY', ...)`. Hashing a non-AES key would
   produce a meaningless id.
3. Miss, `key.extractable === false` -> throw
   `HpkeError('ERR_UNKNOWN_KEY', ...)`. Message must say why: the key
   did not come from this library and cannot be exported.
4. Miss, extractable AES-GCM -> export, derive, cache in the WeakMap,
   return.

Async in both branches. The WeakMap hit is synchronous, but the
export-and-hash fallback is not, and one signature beats a
sometimes-sync/sometimes-async return. Everything else in this package
is already async.

### `verifyKeyId(key, expected)`

```ts
export async function verifyKeyId (
    key:CryptoKey,
    expected:string
):Promise<boolean>
```

Resolves `keyId(key)` and compares. Returns `true` / `false`.

- If `keyId` throws, **let it propagate**. Do not catch and return
  `false` -- that would conflate "cannot check this key" with "this key
  does not match", which is the bug the helper exists to prevent.
- Compare in constant time: bail `false` immediately on length
  mismatch (length is public), otherwise XOR-accumulate char codes over
  the full string and test the accumulator against zero.

Timing is not a real threat here -- these fingerprints are public -- but
the comparison costs nothing to do correctly and callers will copy the
pattern.

## Change 4: `HpkeError`

The original note said "nothing to change in the API" and then asked for
a distinction callers can branch on, which is an API change. Resolving
in favor of the distinction.

Current state is better than the note implies: malformed input already
throws a clear `malformed envelope: too short`. The real gap is that an
AEAD tag mismatch escapes as WebCrypto's bare `OperationError`, with no
library identity and nothing to branch on, so a caller cannot tell
version skew from an attack.

New file `src/errors.ts` (a leaf module -- `src/util.ts` already imports
from `src/index.ts`, so do not deepen that cycle):

```ts
export type HpkeErrorCode =
    | 'ERR_MALFORMED_ENVELOPE'
    | 'ERR_DECRYPT_FAILED'
    | 'ERR_INVALID_KEY_SIZE'
    | 'ERR_KEY_NOT_EXTRACTABLE'
    | 'ERR_INVALID_RECIPIENT'
    | 'ERR_INVALID_KEYPAIR'
    | 'ERR_SMALL_ORDER_KEY'
    | 'ERR_UNKNOWN_KEY'

export class HpkeError extends Error {
    readonly code:HpkeErrorCode

    constructor (
        code:HpkeErrorCode,
        message:string,
        options?:ErrorOptions
    ) {
        super(message, options)
        this.name = 'HpkeError'
        this.code = code
    }
}
```

One class with a `code` string, not a class per failure. This package
ships ESM, CJS, and minified builds of each; if a consumer ends up with
two copies loaded, `instanceof MalformedEnvelopeError` silently returns
`false` while `err.code === 'ERR_MALFORMED_ENVELOPE'` keeps working.
`instanceof Error` still holds either way.

Export `HpkeError` and `HpkeErrorCode` from `src/index.ts`.

### Every throw site

Message text is **preserved verbatim** at every existing site, so the
current regex assertions in `test/index.ts` keep passing.

| Site | Code | Message |
|---|---|---|
| `openRawBytes` short input | `ERR_MALFORMED_ENVELOPE` | `malformed envelope: too short` (unchanged) |
| `decryptBytes` short input (both checks) | `ERR_MALFORMED_ENVELOPE` | `malformed message: too short` (unchanged) |
| `aeadOpen` failure | `ERR_DECRYPT_FAILED` | `decryption failed: wrong key, wrong info, or tampered bytes` |
| `decryptBytes` body `subtle.decrypt` failure | `ERR_DECRYPT_FAILED` | same as above |
| `validateKeysize` | `ERR_INVALID_KEY_SIZE` | `invalid keysize: N (expected 128 or 256)` (unchanged) |
| `validateRawKeyBytes` | `ERR_INVALID_KEY_SIZE` | `invalid aesKey length: N bytes (expected 16 or 32)` (unchanged) |
| `exportAesKeyBytes` | `ERR_KEY_NOT_EXTRACTABLE` | `aesKey must be extractable: its raw bytes are what get sealed` (unchanged) |
| `importRawPublic` bad length | `ERR_INVALID_RECIPIENT` | `invalid public key length: ...` (unchanged) |
| `resolveRecipientPublicKey` non-public `CryptoKey` | `ERR_INVALID_RECIPIENT` | `recipient CryptoKey must be a public key` (unchanged) |
| `resolveRecipientPublicKey` non-public pair member | `ERR_INVALID_RECIPIENT` | `recipient keypair publicKey must be a public key` (unchanged) |
| `resolveRecipientPublicKey` fallthrough | `ERR_INVALID_RECIPIENT` | `unrecognized recipient key form` (unchanged) |
| `assertX25519Algorithm` on a recipient | `ERR_INVALID_RECIPIENT` | `... must be an X25519 key (got X)` (unchanged) |
| `decap` non-private `privateKey` | `ERR_INVALID_KEYPAIR` | `keypair.privateKey must be a private key` (unchanged) |
| `assertX25519Algorithm` on `keypair.privateKey` | `ERR_INVALID_KEYPAIR` | `... must be an X25519 key (got X)` (unchanged) |
| `dh` all-zero output | `ERR_SMALL_ORDER_KEY` | `X25519 shared secret is all-zero (small-order public key?)` (unchanged) |
| `keyId` on an unregistered, unhashable key | `ERR_UNKNOWN_KEY` | new |

Two implementation details:

- `assertX25519Algorithm` is called on both recipient public keys and on
  `keypair.privateKey`. Give it a `code:HpkeErrorCode` parameter so each
  call site supplies the right one, rather than picking one and being
  wrong half the time.
- Wrapping the AEAD failures means putting `try` / `catch` around
  `subtle.decrypt` in `aeadOpen` (`src/util.ts`) and around the body
  decrypt in `decryptBytes` (`src/index.ts`). Attach the original
  `OperationError` as `cause` so it is still available for debugging;
  do not put it in the message.

`ERR_INVALID_KEYPAIR` and `ERR_SMALL_ORDER_KEY` were added after walking
every existing throw site. They cover cases the original six-code
sketch would have had to file under a wrong-fitting code.

## Tests

`test/index.ts` only. `test/node.ts` just re-imports it.

New coverage:

1. `create` / `encryptKey` return `wrapped` (and no `enc` field).
2. `keyId` from `create` matches `keyId(key)` for the same key.
3. `keyId` after `open` equals the `keyId` from `create` -- the round
   trip that makes this feature worth having.
4. `keyId` works on a **non-extractable** key (the whole point):
   `create` with default opts, then `keyId(result.key)` resolves, and
   `result.key.extractable === false`.
5. `keyId` on a foreign extractable AES-GCM key resolves (fallback
   path).
6. `keyId` on a foreign **non-extractable** AES-GCM key rejects with
   `code === 'ERR_UNKNOWN_KEY'`.
7. `keyId` on a non-AES key rejects with `ERR_UNKNOWN_KEY`.
8. `verifyKeyId` returns `true` on match, `false` on a same-length
   mismatch, `false` on a different-length string.
9. `verifyKeyId` propagates (does not swallow into `false`) when the key
   is unknown.
10. Two different keys produce different `keyId`s.
11. Default extractability is `false` for `create`, `encryptKey`, and
    `open`; `{ extractable: true }` yields `true` for each.
12. A supplied `CryptoKey` is returned by identity
    (`result.key === suppliedKey`).
13. Every existing throw-site test additionally asserts `err.code`.
14. `HpkeError` instances satisfy `instanceof Error` and carry
    `name === 'HpkeError'`.
15. The known-answer fixture test is untouched and still passes, proving
    the wire format did not move.
