# simple-hpke 0.4.0 -- supplied-key identity and `verifyKeyId`

Status: implemented 2026-11-02, not yet released (see the Unreleased
section of `CHANGELOG.md`). Decisions are recorded in
`docs/adr/ADR-006-supplied-key-returned-by-identity.md` and
`docs/adr/ADR-007-keyid-from-key-behavior.md`. One addition shipped
beyond this spec: a supplied `CryptoKey` that is not AES-GCM is also
rejected with `ERR_INVALID_AES_KEY`.
Follows: `notes/0.3.0-spec.md`. That spec shipped as 0.3.1 with two items
left open, and this spec closes them. Everything else from 0.3.0 is
done and is not revisited here.

This is a breaking release for one narrow case (see Change 1), so it
ships as 0.4.0 with a `BREAKING CHANGE:` changelog entry. The wire
format does not move.

## Problem Statement

Two gaps remain for a caller holding a long-lived AES-GCM key.

First, when a caller hands `encryptKey` or `encrypt` their own
`CryptoKey`, the library exports its bytes, wraps them, and then hands
back a *different* key object re-imported from those bytes. Since 0.3.0
made re-imported keys non-extractable by default, the caller passes in
an extractable key and receives a downgraded copy. The copy also always
carries `['encrypt', 'decrypt']` regardless of what the caller's key
declared, so a decrypt-only key silently gains the encrypt usage. The
caller has to know to ignore the returned `key` and keep using their
own, which is the opposite of what a return value implies.

Second, `keyId` exists but there is no companion to check a stored id
against a key. Every consumer writes the same comparison by hand, and
the obvious `===` on two strings leaks timing and, worse, invites the
pattern of catching the `keyId` error and returning `false`, which
turns "I cannot fingerprint this key" into "this is the wrong key".

## Solution

`encryptKey` and `encrypt` return the caller's `CryptoKey` object
itself, untouched, when one is supplied. The library only imports a key
when it generated or was given raw bytes.

A new exported `verifyKeyId(key, expected)` resolves `true` or `false`
with a constant-time comparison and lets `keyId`'s own error propagate.

## User Stories

1. As an app holding a room key, I want `encryptKey(recipient, myKey)`
   to return `myKey` itself, so that the key I keep in memory is the
   same object the library reports back and I never accidentally hold
   a weaker duplicate.
2. As an app that imports keys with precise usages, I want the library
   to leave my key's extractability and usages exactly as I declared
   them, so that a decrypt-only key stays decrypt-only.
3. As an app that persists a `keyId` next to stored ciphertext, I want
   `verifyKeyId(key, storedId)` to tell me whether a recovered key is
   the one I expect, so that I do not write the comparison myself.
4. As that same app, I want `verifyKeyId` to throw when the key cannot
   be fingerprinted rather than return `false`, so that a broken key and
   a wrong key are not confused.

## Implementation Decisions

### Change 1: a supplied `CryptoKey` comes back by identity

- When `aesKey` is a `CryptoKey`, `encryptKey` returns `{ wrapped,
  key }` with `key === aesKey`. No re-import happens on this path.
- `opts.extractable` is ignored when a `CryptoKey` is supplied. It
  governs only keys the library imports: a generated key, or raw bytes
  passed as `Uint8Array`. Those two paths are unchanged.
- The input constraints on a supplied key are unchanged: it must be
  extractable (its raw bytes are what get sealed) and must export to 16
  or 32 bytes. Both still throw `ERR_INVALID_AES_KEY`.
- Consequence, accepted: the library no longer launders usages. A
  supplied key without the `encrypt` usage can still be wrapped by
  `encryptKey` (wrapping never calls `subtle.encrypt` with that key),
  but it can no longer be used by `encrypt` / `encrypt.asString`,
  because the message body is encrypted under the caller's own key.
- To keep the invariant that every error this package throws is an
  `HpkeError`, `encrypt` and `encrypt.asString` check a supplied
  `CryptoKey` for the `encrypt` usage up front and throw
  `ERR_INVALID_AES_KEY` with a message naming the missing usage. The
  check happens before any wrapping work. `encryptKey` on its own does
  not perform this check, since wrapping a decrypt-only key is a valid
  thing to want.
- `create` is untouched; it never receives a key.
- `open` is untouched; it has no supplied key and keeps importing with
  `opts.extractable`.

### Change 2: `verifyKeyId`

- Signature: `verifyKeyId(key:CryptoKey, expected:string):
  Promise<boolean>`. Exported from the package entry alongside `keyId`.
- Resolves `keyId(key)` and compares it to `expected`.
- Errors from `keyId` propagate unchanged. The code is the existing
  `ERR_INVALID_AES_KEY` (a non-AES-GCM key, or a key without the
  `encrypt` usage). The 0.3.0 spec's `ERR_UNKNOWN_KEY` is not added:
  the shipped `keyId` derivation works on any usable AES-GCM key, so
  there is no "unregistered key" state to report.
- Comparison is constant time over the string: return `false` at once
  on a length mismatch (length is public; a valid id is always 43
  characters), otherwise XOR-accumulate the char codes across the full
  length and test the accumulator against zero. Timing is not a real
  threat for a public fingerprint, but the pattern is what callers will
  copy, so it should be the right one.
- `verifyKeyId` lives next to `keyId` in the same module, and reads only
  the public `keyId`; it does not touch the derivation internals.

### Docs

- README: in the `keyId` section, add `verifyKeyId` with a short
  example; in the `encryptKey` / `encrypt` reference, state that a
  supplied `CryptoKey` is returned as-is and that `opts.extractable`
  does not apply to it; note that `encrypt` needs the `encrypt` usage
  on a supplied key. Run `npm run toc` after.
- CHANGELOG: a `BREAKING CHANGE:` entry for the supplied-key identity
  change (returned key is the caller's object; usages no longer
  widened; `encrypt` rejects a key without the `encrypt` usage), and an
  `Added` entry for `verifyKeyId`.
- CLAUDE.md Contracts: add `verifyKeyId` and the identity rule for a
  supplied `CryptoKey`.
- JSDoc on `encryptKey`, `encryptBytes`, and `encryptToString`: the
  identity and usage notes above.

## Testing Decisions

Seam: the public API as imported by the shared test suite. This is the
existing seam the whole suite already uses, and no new one is needed.
Tests assert on return values, object identity, `CryptoKey` properties,
and `HpkeError.code`, never on message text or on internals.

Prior art: the existing `encryptKey/open with caller-supplied key` test
(round-trips bytes but never checks identity), the `keyId` block of
tests, and the `thrownCode` helper used by the typed-error tests.

New coverage, all in the shared suite:

1. `encryptKey` with a supplied `CryptoKey` returns that same object
   (`result.key === supplied`).
2. The returned key keeps the supplied key's `extractable` and `usages`
   even when `opts.extractable: false` is passed.
3. `encrypt` with a supplied extractable key that lacks the `encrypt`
   usage rejects with `ERR_INVALID_AES_KEY`.
4. `encryptKey` with that same decrypt-only key succeeds, and `open`
   recovers the same bytes, proving wrap does not need the usage.
5. The existing supplied-key round-trip, raw-bytes round-trip, and
   non-extractable-rejection tests continue to pass untouched.
6. `verifyKeyId` resolves `true` for a key and its own `keyId`, and for
   the `open`-recovered half of a `create` envelope against the created
   key's id.
7. `verifyKeyId` resolves `false` for a same-length string with one
   character changed, and `false` for a string of a different length.
8. `verifyKeyId` rejects with `ERR_INVALID_AES_KEY` for a decrypt-only
   key and for a non-AES-GCM key. It must reject, not resolve `false`.
9. The known-answer fixture test is untouched and still passes.

## Out of Scope

- Adding a `keyId` field to the `encryptKey` / `create` return value.
  Callers can call `keyId(result.key)`. Raise separately if wanted.
- Any change to the `keyId` derivation, label, or output length. It is
  pinned wire format.
- Adding `ERR_UNKNOWN_KEY` or any other new error code.
- Re-exporting `RecipientKey` or `SupportedEncodings`. Still worth
  doing, still its own change.
- Changing `open`, `open.raw`, `decrypt`, or any wire format.
- Updating the stale "not yet implemented" status line in the 0.3.0
  spec, or reconciling its code-name table with what shipped. That is a
  docs housekeeping task, not part of this release.

## Further Notes

The identity change is strictly more capable for callers who were
passing an extractable key and ignoring the copy, and strictly stricter
for callers who relied on the copy to add an `encrypt` usage their key
did not have. The consuming chat app updates in lockstep, so no alias
or compatibility shim is carried.
